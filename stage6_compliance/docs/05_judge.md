## 为什么失败必须拒绝

裁判把回复分成三个词：通过、需修改、拒绝，并给一句原因。我们只收 JSON。模型常会在前面加「好的」，或用 Markdown 围栏包住 JSON。`parse_verdict` 从第一个 `{` 剪到最后一个 `}`，这和阶段 1 剪意图 JSON 是同一类做法。

剪不出来、不是对象、缺 `verdict` 或 `reason`、`verdict` 不在三个词里、原因是空的，都进 `closed_verdict`。结论是拒绝，`ok` 是 `False`，原因固定为「审核结果无法解析，默认拒绝，不放行」。

默认放行是这一课要避免的坑。裁判宕了、网络断了、模型说「今天天气不错」，若当成通过，后面的回复会原样发给顾客。`llm_judge` 在接口抛错时也走同一条关闭，不把异常打印成崩溃后继续。👉 不懂 try？先看 [基础课 · try / except](../../00_python_basics/16_try_except.md)。

`all(key in data for key in ("verdict", "reason"))` 要求两个字段都在。缺 `reason` 的 `{"verdict":"通过"}` 因此关闭。空的字段名单不能拿去 `all`，空名单会是真。这里的名字是写死的两个。

`hits_from_verdict` 把通过收成零条命中，把需修改收成中 / 改写，把拒绝和关闭收成高 / 拦截。词表若已经命中，第 7 课会取更严重的那条。裁判说通过，取消不了词表。

## 屏幕上的七段

1. 纯 JSON「通过」：ok 为 True，收成低 / 放行。
2. 前面有「好的。」的「需修改」：仍能剪出对象，收成中 / 改写。
3. Markdown 围栏里的「拒绝」：ok 为 True，收成高 / 拦截。这是合法的拒绝，不是解析失败。
4. 「今天天气不错」：ok 为 False，原因是那句固定的关闭说明。
5. `verdict` 为「也许」：不在三个词里，关闭。
6. 只有 `verdict`、没有 `reason`：关闭。
7. 空字符串：关闭。

有密钥时，后半段会把两句写好的回复交给 DeepSeek。一句在政策内，一句在乱承诺。没有密钥时你看不到这两行的模型原文，解析已经说明关闭规则。

## 常见坑

- `except` 里返回通过，或者什么都不返回。调用方会把「没有意见」当成放行。
- 只检查 `verdict`，不检查它是不是那三个词。模型写「也许」也会被放行。
- 把裁判的回复直接给顾客。裁判不是客服。顾客看到的是 `decide` 之后的模板或改写，不是 JSON。
- 把未打码的号码送给裁判。`review_output` 先打码，再调用 `judge_fn`。

## 练习

1. `{"verdict":"通过"}` 为什么不能通过？
2. 围栏里的拒绝，`ok` 为什么仍是 True？
3. 网络失败时，为什么不能把上一句回复原样发出去？

## 答案

1. 没有 `reason`。`all` 失败，走关闭。原因不能为空，否则日志里看不出裁判在拒绝什么。
2. 花括号里的对象合法，三个词也对，原因也不是空的。围栏只是前后的废话，剪掉之后还在。
3. 失败和「模型认为可以」不是一回事。原样发出去等于审核没有发生。关闭用拦截模板代替原文。
