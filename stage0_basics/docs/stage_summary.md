# 阶段小结：你现在真正会了什么

四课之后，星河数码的客服仍然不会查订单、不会在你关掉终端后记得你、也不会在回复发出去之前做检查。这不是失败。阶段 0 要会的是看清一次调用，以及看清「还缺哪几块」。

下面每件事都应该能离开代码，用自己的话讲出来。讲不出的，回到对应的课重做那个实验，而不是把注释再读一遍。

## 你应该能讲清楚的七件事

1. **一次调用是一份 JSON 的来回。** 正文在 `choices[0].message.content`。停的原因在 `finish_reason`。长度在 `usage`。密钥在请求头里，不在正文里。见 [第 1 课](01_hello_llm.md)。
2. **创建客户端不联网。** 花钱和失败发生在 `create()`。缺密钥应该在那之前被 `config.py` 拦住。见 [课前](00_config.md)。
3. **三种角色不是三种记忆。** `system` 是岗位说明，`user` 是顾客，`assistant` 是模型已经说过的话。见 [第 2 课](02_messages_roles.md)。
4. **接口无状态。** 下一轮看得到上一轮，只因为本地列表被整包重发。`prompt_tokens` 因此变大。
5. **流式给的是增量。** 屏幕上的字不会自动变成历史。`"".join` 之后的那一条字符串才会。见 [第 3 课](03_streaming.md)。
6. **循环负责边界。** 退出和空行不要发给模型；失败的半轮不要留在列表里。见 [第 4 课](04_cli_chatbot.md)。
7. **系统提示不是工具，也不是法规。** 它降低某些说法的倾向，不查询数据库，也不拦截银行卡号。

名词忘记时查 [名词表](glossary.md)。

## 同一个限制，后面每一阶段各补一块

阶段 0 的列表什么都往里放：岗位说明、最近几句、你希望它遵守的政策。这在两轮对话里刚好够用。它同时撞上四堵墙。

| 你在阶段 0 撞上的墙 | 只靠把字放进 `messages` 为什么不够 | 后面哪一阶段处理 |
| --- | --- | --- |
| 每句话都直接送给模型，打招呼和退货走同一条路 | 模型可以顺便闲聊，但程序无法决定「这句话该不该查库」 | 阶段 1 意图识别：先分类，再选择后续步骤 |
| 问物流时它只能说「我查不到」，或者说了也是编的 | 系统提示里没有订单表。文字不会变成 SQL | 阶段 2 工具调用：模型请求一个函数，程序用 SQLite 查询或建工单，再把结果写回消息 |
| 终端一关，列表就没了；列表太长又送不起 | 变量不是存储。整包重发受上下文窗口和费用限制 | 阶段 3：把这一轮正在办的事（工作记忆）和最近这段会话（短期记忆）放到 Redis，而不是永远堆在一个列表里 |
| 退货政策若只写在系统提示里，提示会又长又旧 | 岗位说明适合短规矩，不适合整本手册。手册放进去会占满窗口 | 阶段 4 RAG：先从店铺文档里检索相关段落，只把查到的几段放进这一次请求 |
| 顾客下周再来，不该把上周全部闲聊都塞回去，但有些偏好值得留 | 无状态接口不记得「这个人喜欢工作日送货」 | 阶段 5 长期记忆：把值得保留的事实做成向量，用 FAISS 找回来，而不是回放整段聊天记录 |
| 提示写了不要卡号、不要乱承诺，模型仍可能说漏 | 提示不是检查器。输入和输出都还没经过程序审查 | 阶段 6 合规审查：在调用前后用代码挡敏感信息和过度承诺 |
| 现在只有一个手写的 `while` | 分支、工具、审查一多，全写在这个循环里会缠住 | 阶段 7：把它们收成明确的智能体循环，并用 FastAPI 提供给调用方 |

请特别分开三种「记得」：

- **这一次进程里的 `messages`**：阶段 0 已有。退出程序就丢。
- **短期记忆**：同一次购物咨询在几分钟或几小时后还能续上，存在 Redis 里，装回列表时通常只取最近一段，而不是从开店第一天开始。
- **长期记忆**：跨很多次咨询仍有用的少量事实，用检索找回来，不是把旧 transcript 全部贴上。
- **RAG**：店铺写好的政策文档，不是顾客的个人事实。它解决「模型没读过我们的退货条款」，不解决「这个顾客上次说了什么」。

把这四样都叫成「让 AI 有记忆」，后面的设计会乱。

## 阶段 7 的循环，用你现在的词先说一遍

现在的循环是：

```text
读一行 → 是不是退出 → 追加 user → create() → 追加 assistant
```

以后大体会变成：

```text
读入顾客的话
→ 意图识别（阶段 1）
→ 需要事实时调用工具或检索（阶段 2、4、5）
→ 需要时从 Redis 装入近期会话（阶段 3）
→ 仍用一次 chat.completions 生成回复（阶段 0 的那次请求）
→ 审查回复（阶段 6）
→ 写回短期记忆，再显示给顾客
```

中间无论加多少块，对模型的那一下仍然是：一份带角色的 `messages`、一个 `model`、可选的温度和长度。流式只改变显示和拼接，不改变「历史里要有一条完整 assistant」。
